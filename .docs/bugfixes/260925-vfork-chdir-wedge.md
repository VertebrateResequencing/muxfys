- [x] A process that serves a muxfys mount and starts a child process whose working directory (exec.Cmd.Dir) is on that mount can deadlock forever. wr's runner does exactly this for a job with mounts and no explicit Mount, where the job's cwd is the mount root.
  - Go forks with CLONE_VFORK. The child chdirs before exec, and the chdir sends a FUSE_ACCESS request, because muxfys's Access (filesystem.go:935) returns fuse.OK and so the kernel keeps asking. Only the parent can answer. If a GC stop-the-world starts in that window, it can never preempt the vforking thread, so no goroutine serves the request and the process wedges for good. See golang/go#11155, and go-fuse fs/api.go:152-176.
  - A realistic rate on Go 1.26.3, natural GC with 1 MB/s of allocation: about 1 wedge per 830 execs.
  - Red: standalone go-fuse harness scratchpad/fusefork-w1/ (w1_test.go, matrix.sh), with Access OK and a 1s TTL, cwd = mount root, and an exec loop under forced GC: `TRIALS=5 ./matrix.sh w1263.test go1.26.3 baseline=` gives `wedged=5/5`.
  - Proven workaround, same harness: Access returns ENOSYS, plus one access(2) on the mount root made by the serving process itself before any exec, so the kernel learns ENOSYS from a request that nothing else is waiting on. Result: `enosys-warm wedged=0/5` on both 1.25.5 and 1.26.3. The chdir then sends no FUSE request at all. There's no permission-semantics change, because Access already allowed everything.
  - Not covered: a cwd in a SUBDIRECTORY of the mount would also need long entry/attr timeouts. wr uses the mount root, so that's out of scope; document it.
  - Fixed. `MuxFys.Access` (filesystem.go) now returns `fuse.ENOSYS`, and `Mount()` (muxfys.go) calls `syscall.Access(mountPoint, X_OK)` itself straight after `WaitMount()`, so the kernel sets `no_access` from a request nothing else waits on. Every later access check, a chdir's included, is granted without a FUSE request. The `Mount()` doc comment and the README's Guidance section say a child's cwd must be the mount root, since a subdirectory would also need long entry/attr timeouts.
  - Regression test `TestMountForkChdir` (access_test.go) mounts real muxfys over the test `localAccessor`, in a re-exec'd copy of the test binary, then execs `/bin/true` with `cmd.Dir` on the mount root for 1s under back-to-back `runtime.GC()`. The parent treats 2s without output as a wedge. It then kills the child's process group, aborts only that mount's fusectl connection (the minor of its `0:N` st_dev in `/proc/self/mountinfo`, matched by mount point and `fuse.MuxFys` fstype, and rechecked before the abort), and runs `fusermount -u -z`. It pins 3 trials and skips if `/dev/fuse` or fusermount is unusable.
  - Red before the fix: `CGO_ENABLED=0 go test -tags netgo --count 1 . -run TestMountForkChdir` gave `wedged 3/3` on each of 4 runs (6.2s). With ENOSYS but without Mount's warm-up access it still wedged 2/3, so the warm-up is load-bearing. After the fix it passes 3/3 in 3.1s, on 5 plain runs and 2 `-race` runs. No mount, fusectl connection or process was left behind by any run.
  - `TestMountAccess` shows permissions are unchanged on a writable cached mount: `access(2)` with R|W|X succeeds on the root, a remote file and a created file, and `test -r`, `test -w` and `test -x` on the root and `test -w` on both files exit 0.
  - Gates: `make lint` 0 issues; `make test`, `make race` and `make coverage` ok (56.4%). `TestS3Localntegration` skips here, as it already did, because minio isn't installed.
