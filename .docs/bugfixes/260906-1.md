# Bugfixes 2026-09-06

- [x] `(*MuxFys).Unmount` deletes a temporary cache directory even when the
  upload of the files it holds failed, destroying the only copy of data
  written to a writable `CacheData` mount. `uploadCreated()` runs, its error is
  folded into the return value, and then every `cacheIsTmp` remote has its
  cache `os.RemoveAll`ed unconditionally (`muxfys.go:474-491`,
  `remote.go:474-478`). Because nothing reaches the remote until Unmount, a
  failed upload (expired credentials, policy change, network partition, full
  remote) is immediately followed by deletion of the output that failed to
  upload. The caller is told the upload failed but not that the data is gone.
  `cacheIsTmp` is true whenever `CacheData` is on and `CacheDir` is empty,
  which is the documented default, so the destructive path is the common one.

  - Red command:
    `MUXFYS_REMOTES3_TARGET=https://cog.sanger.ac.uk/sb10/wr_tests CGO_ENABLED=0 go test -tags netgo -run TestS3RemoteUnmountUploadFailure -count 1 .`
  - Real vs simulated: the S3 accessor, its credentials (from `~/.s3cfg`), the
    endpoint, the mount-time bucket listing and the FUSE mount and write are
    all real. Only `UploadFile` is forced to fail, via a wrapper accessor, so
    the failure is deterministic and the bucket is never damaged.
  - Red output (5/5 runs, ~0.1s each):

    ```
    Given a writeable CacheData mount whose upload will fail ✔✔✔✔✔✔✔✔
      Unmount() reports the failure and does not destroy the un-uploaded data ✔✘

    Failures:

      * /home/ubuntu/muxfys/s3_test.go
      Line 3369:
      Expected     ''
      to NOT equal ''
      (but it did)!

    --- FAIL: TestS3RemoteUnmountUploadFailure (0.05s)
    ```

    The empty string is the result of searching the whole cache base for a
    file holding the data that was written to the mount: after Unmount there
    is no copy of it anywhere.

  - Fix: `Unmount` now asks `unuploadedCache()` which remote still holds
    un-uploaded files (`fs.writeRemote` with `cacheData` and a non-empty
    `fs.createdFiles`, read under `mapMutex` after `uploadCreated` and before
    the reset), skips only that one remote in the cache-deletion loop, and
    appends the kept cache path to the returned error. Every other
    `cacheIsTmp` cache, and a write cache that drained successfully, is still
    deleted. `Unmount(true)` deletes as before: the caller asked for no
    upload, so nothing failed and there is no error to carry a path; the doc
    comment now states that.
  - Files: `muxfys.go` (fix, new unexported `unuploadedCache`, `combineErrors`
    and `errKeptCache`, doc comment), `muxfys_test.go` (updated the existing
    error-message assertion, still exact, plus regression tests for cache
    survival, `Unmount(true)`, and only-the-failing-remote's-cache-is-kept),
    `s3_test.go` (the real-S3 red test), `CHANGELOG.md`.
  - Mutation check: restoring the unconditional `if remote.cacheIsTmp {`
    turns `TestS3RemoteUnmountUploadFailure` and `TestMuxFys` red again with
    `go vet ./...` clean.
  - Gates: `make lint` -> `0 issues.`; `make test` -> `ok ... 28.665s`;
    `go build ./...` and `go vet ./...` clean; red command passes. FUSE mount
    count 1 before and after.

- [x] `muxfys.go` hand-rolls `combineErrors(a, b error)` when the standard
  library has `errors.Join`. The repo has no error-combining dependency of any
  kind, `"errors"` is already imported in `muxfys.go`, and `go.mod` declares
  `go 1.26.3`, so `errors.Join` (Go 1.20+) is available. Before this branch the
  `a; b` pattern existed in exactly one place (`muxfys.go:479` on develop,
  `err = fmt.Errorf("%s; %s", err.Error(), uerr.Error())`), so two call sites do
  not justify reimplementing a stdlib function.
  - Source: repo owner, PR #39 review.
  - Behaviour change: `errors.Join` separates messages with `\n`, not `"; "`,
    so the combined `Unmount()` error text changes. `errors.Is` unwrapping is
    unaffected: `Join(a, nil)` is a, `Join(nil, nil)` is nil, and `Join(a, b)`
    matches both.
  - Red command (run from a scratch copy of the repo with the target
    assertion already written, so the working tree stayed clean):
    `CGO_ENABLED=0 go test -tags netgo -run 'TestMuxFys$' -count 1 .`
  - Red output:

    ```
      Expected: "failed to upload 1 files\nthe un-uploaded data has been left in the cache directory <cacheDir>"
      Actual:   "failed to upload 1 files; the un-uploaded data has been left in the cache directory <cacheDir>"
      (Should equal)!

    --- FAIL: TestMuxFys (20.17s)
    ```

  - Fix: both call sites in `Unmount` now call `errors.Join`, and
    `combineErrors` and its doc comment are deleted. No import changed:
    `"errors"` was already imported and `fmt` is still used elsewhere in the
    file.
  - Separator audit: `muxfys_test.go:535` was the only dependency on `"; "`
    anywhere in the repo, and its exact-match assertion now expects `"\n"`.
    `s3_test.go:3387` matches the cache path as a substring and is unaffected;
    the semicolon in `CHANGELOG.md:11` is ordinary prose; `README.md` quotes no
    error text. `grep` for `"; "`, `%s; %s`, `%w; %w`, `; %w` and `; %s` across
    the Go source now returns nothing. The known external consumer, `wr` at
    `jobqueue/client.go:2595`, substring-matches `"failed to upload"`, so the
    separator does not reach it.
  - Newline in logs: `Unmount`'s error reaches log15 at `muxfys.go:437`.
    log15 v3.2.1 `escapeString` rewrites `\n` as two characters inside the
    quotes it was already adding, so logfmt output stays on one line.
  - Equivalence, since a refactor has no red for the unwrapping half:
    `errors.Join(a, nil)` keeps a's message and `errors.Is`, `Join(nil, nil)`
    is nil, `Join(a, b)` matches both. The old helper's both-non-nil branch was
    `fmt.Errorf("%w; %w", a, b)`, already a multi-error, so that case is
    structurally identical. The only delta beyond the separator is that
    `Join(a, nil)` wraps rather than returning `a` itself, so `err == a`
    identity no longer holds; nothing in the repo uses `errors.As`, `Unwrap()`,
    an error type assertion, or `==` against a sentinel.
